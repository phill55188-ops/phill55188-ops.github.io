# Independent cold review 2 — follow-up research

Reviewed 2026-11-17. Scope: frontend followup.js/followup.css and index.html integration, Worker /api/followup, provided node tests. No implementation changes. All external research/provider traffic in this review was mocked; no credentials read or live service calls made.

## Findings

### P2 — reopening Claims follow-up sends obsolete section findings

Location: followup.js:119–123; index.html renderClaims and cross-source evaluation.

A session stores selected section text only the first time its stable card ID is opened. In Evidence check mode, `renderClaims(claims, [])` makes Claims usable before the later cross-source pass finishes; `renderClaims(claims, checks)` then replaces the same card contents. If the user opened the follow-up between these passes, reopening it after cross-source comparison continues to show/send the first snapshot. A contradiction or revised assessment in the now-visible section is omitted from the research request. Its title still identifies the current section, so the stale state is not apparent.

Reproduction: open Claims follow-up after primary claim extraction, close it, let cross-source comparison finish, reopen, and ask about the updated evidence. The request uses the original `session.section.text`. Independent VM fake-DOM harness `/tmp/sb-review-2/frontend.mjs` reproduces card replacement and observes:

```
visibleSection: Updated cross-source claim: independent evidence contradicts the claim.
sentSection: Original primary-source claim; not independently checked.
```

Suggested repair: compare current card text against the session snapshot on each opening; refresh or invalidate the session when rendered analysis changes. Define what prior answers mean after section replacement. Verify with a deferred cross-source integration case.

### P2 — every long answer opens at its bottom

Location: followup.js:57.

`renderAnswers()` always assigns `answer.scrollTop = answer.scrollHeight`. On the first long response this skips directly past its opening, conclusion and most analysis to the last viewport. Reopening an existing long answer also forces it to the bottom, losing the user's reading position. With multiple turns this shows the end of the newest answer rather than the beginning of that answer.

Reproduction: submit a question whose mocked research response is longer than the answer height cap. The independent frontend harness records a requested scrollTop of 1000 with a clientHeight of 480; a real DOM clamps this to the bottom. This is a deterministic code-path finding; visual browser rendering was not performed by this reviewer.

Suggested repair: scroll to the start of the newly inserted turn (first answer starts at zero), and preserve scroll position when simply reopening a section. Check long first answer and long second answer in the real browser.

### P3 — structurally malformed upstream JSON escapes the API error envelope

Location: cloudflare-worker/worker.js:105–109, also extractText.

Readable provider JSON is assumed to have valid nested arrays and non-null annotation objects. A mocked successful response of `{"output":[{"type":"message","content":[{"type":"output_text","text":"A source supports this.","annotations":[null]}]}]}` causes an uncaught TypeError (`Cannot read properties of null (reading 'type')`) rather than the promised JSON 502. A provider/proxy regression can therefore turn a recoverable research failure into a platform exception. This input is not generated by an ordinary user action, so priority is lower.

Independent reproduction: `/tmp/sb-review-2/worker.mjs`. Suggested repair: validate expected output arrays/objects or wrap extraction in a bounded error handler that returns the existing 502 envelope. Add a malformed-shape case alongside unreadable JSON tests.

## Interface/security observations

- Answer and filename rendering use textContent, avoiding HTML injection. Backend citation filtering permits only HTTP(S), excludes embedded credentials, and client links use noopener/noreferrer.
- The dedicated follow-up route uses server-owned instructions; client `system` cannot replace them. Auth and origin checks precede provider requests. Request streaming is bounded to 18 MiB; evidence counts, byte sizes, formats, and total text are bounded.
- Optional evidence is genuinely optional at client and server boundaries.
- CSS reuses the existing theme variables and fonts. Answer height has a natural content height subject to min-height and max-height, with overflow-y:auto. Actual mobile fitting, focus behavior, scrollbar behavior, and branding still require visual browser checks.
- Markdown answer text is currently rendered literally in a paragraph, and annotation offsets are discarded; sources are clickable only in the separate source list. A real answer should be inspected for readable heading/citation presentation.
- No evidence found here establishes live deployment, full provider research quality, or cancellation of an already billed server request. The API documentation correctly distinguishes client cancellation from server cancellation.
